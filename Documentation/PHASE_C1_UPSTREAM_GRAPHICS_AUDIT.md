**Project:** Cricket Legacy (EA SPORTS Cricket 07 Mobile Port)  
**Milestone:** Phase C.1

**Status:** **AUDIT COMPLETE**

---

## 1. Executive Summary

This audit examines the original Direct3D 8 graphics compatibility implementation in `Dhaiwat10/cricket07-browser` to establish an exact, dependency-aware integration path for Android native execution.

The upstream graphics subsystem is structured as a decoupled two-layer pipeline:
1. **Direct3D 8 Frontend (`host/d3d8.c`, `host/d3d8.h`):** Emulates DirectX 8.1 COM objects (`IDirect3D8`, `IDirect3DDevice8`, `IDirect3DTexture8`, `IDirect3DVertexBuffer8`, etc.) and maintains the full Direct3D pipeline state.
2. **Command Recorder (`host/render_rec.c`, `host/render_cmd.h`):** Consumes D3D8 draw calls and states, evaluates transformations/materials, converts texture formats to RGBA8 via `host/texconv.c`, compiles shaders via `host/vshader.c` and `host/pshader.c`, and emits self-contained binary command packets (`Cmd*`).
3. **WebGPU Executor (`host/render_wgpu.c`):** Owns all WebGPU objects (`WGPUInstance`, `WGPUAdapter`, `WGPUDevice`, `WGPUQueue`, `WGPUSurface`, `WGPURenderPipeline`), manages swapchains, and executes render passes.

Our analysis confirms that **over 90% of the upstream graphics code is portable C that can be reused directly**. The only required adaptations pertain to window surface creation (`ANativeWindow`), Vulkan swapchain capabilities, and removing desktop/browser-specific dependencies.

## 2. Component-by-Component Architectural Audit

### 2.1 Direct3D 8 API Implementation (`host/d3d8.c`, `host/d3d8.h`)
- **Mechanism:** Implements 97 methods of `IDirect3DDevice8` and 16 methods of `IDirect3D8` using lightweight COM dispatch (`host/com.c`).
- **State Representation:** Encapsulated in `Device` and `DevState` structures:
  - 256 Render States (`rs[256]`) including `ZENABLE`, `CULLMODE`, `ALPHABLENDENABLE`, `SRCBLEND`, `DESTBLEND`.
  - 8 Texture Stages with 32 Texture Stage States each (`tss[8][32]`).
  - 512 Transform Matrices (`transform[512][16]`) for World, View, and Projection matrices.
  - Viewport definition (`viewport`: x, y, w, h, minz, maxz).
  - Material and 8 hardware light definitions.
- **Portability Assessment:** **100% REUSABLE DIRECTLY**. State tracking logic is completely platform-independent C.

### 2.2 Device Creation (`d3d_CreateDevice` in `host/d3d8.c`)
- **Mechanism:** Allocates a `Device` struct, creates backbuffer and depth surfaces via `new_surface()`, sets standard Direct3D 8 default render states and texture stage states, and initializes the backend via `g_render->init(d)`.
- **Portability Assessment:** **REUSABLE WITH ADAPTATION**. On Android, backbuffer dimensions must match the Android `SurfaceView` / `ANativeWindow` resolution rather than desktop fixed 640x480 / 800x600 windows.

### 2.3 Vertex and Index Buffers (`Buffer` in `host/d3d8.h`, `d3d8.c`)
- **Mechanism:**
  - Vertex Buffers (`IDirect3DVertexBuffer8`) and Index Buffers (`IDirect3DIndexBuffer8`) are allocated in guest memory (`mem` offset).
  - Locking (`Lock`) returns guest pointers for CPU writes.
  - In `dev_DrawPrimitive` and `dev_DrawIndexedPrimitive`, stream bindings (`stream_vb[16]`) and index buffers (`ib`) are passed to `g_render->draw`.
- **Portability Assessment:** **REUSABLE DIRECTLY**. Operates seamlessly with our validated 4GB Virtual Memory Arena (`HP(mem)` translates 32-bit offsets to host memory).

### 2.4 Textures and Surfaces (`Texture`, `Surface`, `host/texconv.c`)
- **Mechanism:**
  - Tracks 2D and Cube textures with mipmap chains (`mem[6][14]`).
  - Dirty versions (`version`) are tracked. When modified, `render_rec.c` detects the version increment and triggers `texture_to_rgba8()` in `host/texconv.c`.
  - Supports DXT1, DXT2, DXT3, DXT4, DXT5, P8 (paletted 256-color), RGB565, ARGB1555, ARGB4444, and ARGB8888.
- **Portability Assessment:** **REUSABLE DIRECTLY**. `host/texconv.c` is pure mathematical C decoding blocks to raw RGBA8.

### 2.5 Shaders and Compilation (`host/vshader.c`, `host/pshader.c`)
- **Mechanism:**
  - **Fixed Function:** Replicated via an embedded WGSL "uber shader" (`WGSL_COMMON` in `render_wgpu.c`).
  - **Vertex Shaders:** Handled either via CPU software processing (`vs_run` in `vshader.c`) or translated into WGSL `vs_gpu` functions (`vs_to_wgsl`).
  - **Pixel Shaders (ps.1.1):** Dynamically transpiled to WGSL fragment shader text by `pshader.c`.
- **Portability Assessment:** **REUSABLE DIRECTLY**. The WGSL text generated by `pshader.c` and `vshader.c` adheres to standard WebGPU WGSL specifications supported by `wgpu-native`.

### 2.6 Render State & Pipeline Management
- **Mechanism:**
  - The recorder computes a 64-bit pipeline key (`PKey`) representing blend state, depth/stencil state, topology, and shader IDs.
  - The executor (`render_wgpu.c`) caches `WGPURenderPipeline` objects in a hash table keyed by `PKey`.
- **Portability Assessment:** **REUSABLE DIRECTLY**. Zero platform-specific assumptions.

### 2.7 Depth Buffers and Depth Testing
- **Mechanism:**
  - Backbuffer depth format is `WGPUTextureFormat_Depth24PlusStencil8`.
  - `exec_target` manages scratch depth textures when render target sizes do not match.
  - Depth comparison functions (`D3DCMP_LESSEQUAL`, `D3DCMP_ALWAYS`, etc.) map to `WGPUCompareFunction`.
- **Portability Assessment:** **REUSABLE DIRECTLY**. `wgpu-native` Vulkan on Android supports `Depth24PlusStencil8` natively.

### 2.8 Command Stream Protocol (`host/render_cmd.h`)
- **Mechanism:**
  - Commands (`CMD_TARGET`, `CMD_CLEAR`, `CMD_DRAW`, `CMD_UPLOAD_TEX`, `CMD_PRESENT`, etc.) are queued into `g_cb`.
  - In native desktop builds (`#ifndef __EMSCRIPTEN__`), commands are flushed immediately via `gpu_exec(h)`.
- **Portability Assessment:** **REUSABLE DIRECTLY**. The synchronous native execution mode fits Android native threads perfectly.

### 2.9 Window Creation, Resize, and Presentation
- **Mechanism:**
  - Desktop macOS implementation hardcodes `g_metal_layer` and SDL2 window polling.
  - Desktop presentation copies offscreen `g_bb` to `cur.texture` and calls `wgpuSurfacePresent(g_surface)`.
- **Portability Assessment:** **REQUIRES ANDROID ADAPTATION**.
  - Must replace `g_metal_layer` with `ANativeWindow` surface instantiation (`WGPUSurfaceDescriptorFromAndroidNativeWindow`).
  - Must adapt swapchain presentation to handle Android Vulkan surface formats (`BGRA8Unorm`) and dynamic alpha modes (`WGPUCompositeAlphaMode_Inherit`).
  - Must integrate surface resize hooks (`cricket_wgpu_resize`).

### 2.10 Browser / Emscripten Dependencies
- **Audit Findings:**
  - `__EMSCRIPTEN__` blocks contain browser canvas resizing (`rc_set_canvas_size`), event pump loops (`rc_gpu_pump`), and async readbacks.
  - Native path (`#ifndef __EMSCRIPTEN__`) already exists in upstream and contains the synchronous `gpu_exec` loop and `gpu_init_native()`.
- **Portability Assessment:** **CLEAN SEPARATION**. Compiling with `__ANDROID__` (and without `__EMSCRIPTEN__`) activates the native desktop execution path automatically.

## 4. Conclusion & Action Plan for Phase C.1

The upstream graphics code is exceptionally modular and directly portable to Android native. 
We will now:
1. Implement the Android host backend adaptation in `android-native-prototype/src/` to connect `ANativeWindow` into `render_wgpu.c`.
2. Integrate `d3d8.c`, `render_rec.c`, `render_wgpu.c`, `vshader.c`, `pshader.c`, and `texconv.c` into `libcricket_native_harness.so`.
3. Construct a validation scene that executes the original `IDirect3DDevice8` calls to prove hardware rendering on Android 14.
