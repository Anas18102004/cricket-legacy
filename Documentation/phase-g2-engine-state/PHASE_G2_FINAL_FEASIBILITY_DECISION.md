# Final Feasibility Decision

## Verdict: PARTIALLY PROVEN

The renderer exposes a useful, atomic, read-only coarse context signal and the native/Java lifecycle invalidates stale samples. This is a valid future fail-closed boundary for distinguishing menu-like/panel rendering from open 3D rendering.

The required original match-state discovery is incomplete. No trustworthy source currently identifies batting role, bowling stage, ball lifecycle, running acceptance/cancellation, fielding phase, wicket, over, innings, or match completion. State-machine RTTI and autogenerated function names are leads for further reverse engineering, not proof. The candidate `0x008A1000` global is unsupported and must be discarded as an integration source unless independently verified.

Settings-menu integration and exact action mapping are also not established. No original menu was changed. Automatic fielding code was not modified, but no gameplay catch test was completed.

## Acceptance constraints

- Keep G.1 controls hidden by default and preserve original touch delivery.
- Do not gate/show gameplay HUD from renderer context alone.
- Do not use timers or the unverified global.
- Require symbol/field recovery and actual interactive transition evidence before implementing precise contexts.
- Require runtime screenshots and gameplay tests for any future acceptance verdict.

This phase advances discovery but does not satisfy contextual HUD implementation or actual gameplay acceptance.
