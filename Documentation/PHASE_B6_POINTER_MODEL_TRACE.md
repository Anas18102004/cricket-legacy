## 1. How the Recompiler Actually Translates x86 Instructions to C

In Dhaiwat10's `cricket07-browser` / `retro-port`, the static recompiler (`translator/x86toc.py`) reads 32-bit Windows PE machine code disassemblies (produced by Ghidra/Capstone) and emits C functions (`out_all/*.c`).

### 1.1 The Address Space Model
In 32-bit Windows, the original `Cricket07.exe` image is loaded at PE base `0x00400000`. Its `.text` code section occupies `0x00401000` to `0x00780000`, its `.rdata` and `.data` static variables occupy `0x00780000` to `0x00A50000`, and dynamic heaps grow upwards from `0x01000000`.

In `x86toc.py`:
- In **WebAssembly (wasm32)**, linear memory is a single contiguous array indexed from `0x0` to `0xFFFFFFFF`.
- In **Native 64-bit compilation (macOS / Linux / Android)**, native pointers are 64 bits wide (`uintptr_t`).
- The recompiler emits direct memory dereferences against an execution memory base.

## 2. Five Real Generated C Memory Access Patterns

Below are the five canonical memory operations generated by `x86toc.py` and how they behave on a 64-bit host:

### Pattern 1: A Translated Function Reading an Original x86 Address
*Original x86 Instruction:*
```assembly
MOV EAX, DWORD PTR [0x008A4120]    ; Read global pitch friction coefficient
```
*Generated C Translation in `out_all/` (Direct Pointer Model):*
```c
uint32_t eax = *(const uint32_t*)(uintptr_t)0x008A4120;
```
*How it behaves on 64-bit Host:*
- The 32-bit constant `0x008A4120` is zero-extended to 64-bit `0x00000000008A4120`.
- **Under Strategy 1 (`ARENA_MODE_FIXED_LOWER_4GB`):** Because virtual memory `0x00010000` to `0x100000000` is mapped directly in the host process, the CPU dereferences `0x008A4120` natively in a single `LDR` instruction with zero translation overhead.
- **Under Strategy 2 (`ARENA_MODE_BASE_OFFSET`):** If low memory had a collision, the memory access macro evaluates:
  ```c
  uint32_t eax = *(const uint32_t*)((uint8_t*)g_ram + 0x008A4120);
  ```

---

### Pattern 2: A Translated Function Writing to an Original x86 Address
*Original x86 Instruction:*
```assembly
MOV DWORD PTR [ECX + 0x14], EDX    ; Write bowler speed into entity struct field
```
*Generated C Translation in `out_all/`:*
```c
*(uint32_t*)(uintptr_t)(ecx + 0x14) = edx;
```
*How it behaves on 64-bit Host:*
- `ecx` holds an original 32-bit heap address (e.g., `0x02150000`).
- `(ecx + 0x14)` evaluates to `0x02150014` in 32-bit integer arithmetic.
- Cast to pointer `(uintptr_t)` zero-extends to `0x0000000002150014`.
- Under Strategy 1, the store writes directly to physical page backing `0x02150014`.
- Under Strategy 2, `(g_ram + 0x02150014)` computes the host pointer.

---

### Pattern 3: Reading a Pointer Stored Inside Game Memory (C++ VTables & Linked Lists)
*Original x86 Instruction:*
```assembly
MOV EDX, DWORD PTR [ECX]           ; Read C++ vtable pointer from object header
CALL DWORD PTR [EDX + 0x08]        ; Call virtual method #2 (e.g. OnBallContact)
```
*Generated C Translation in `out_all/`:*
```c
uint32_t edx = *(const uint32_t*)(uintptr_t)ecx;
uint32_t target_fn = *(const uint32_t*)(uintptr_t)(edx + 0x08);
recomp_call(target_fn);
```
*How it behaves on 64-bit Host:*
- **The Critical 64-bit Trap:** The pointer stored inside the object at `[ecx]` is a **32-bit integer** (`0x00720480`).
- If a naive implementation had stored native 64-bit pointers into game memory, writing an 8-byte pointer into a 4-byte struct field would corrupt adjacent member variables (`ecx + 4`).
- Because `x86toc.py` stores **all pointers in game memory as 32-bit integers**, and resolves function targets via an indirect jump table `recomp_call(uint32_t target_addr)`, the data layout remains strictly 32-bit binary compatible!

---

### Pattern 4: Pointer Arithmetic with Negative Offsets & Stack Frames
*Original x86 Instruction:*
```assembly
MOV EAX, DWORD PTR [EBP - 0x1C]    ; Read local variable from stack frame
```
*Generated C Translation in `out_all/`:*
```c
uint32_t eax = *(const uint32_t*)(uintptr_t)(ebp - 0x1C);
```
*How it behaves on 64-bit Host:*
- `ebp` is an offset within the recompiled thread's dedicated stack arena (e.g., `0x0019F000`).
- `ebp - 0x1C` performs 32-bit unsigned subtraction: `0x0019F000 - 0x1C = 0x0019EFE4`.
- On 64-bit hosts, if `ebp` were evaluated in 64 bits, negative offsets from low addresses could underflow into sign-extended `0xFFFFFFFFFF...`.
- Ensuring that all address arithmetic operands are `uint32_t` before casting to `uintptr_t` guarantees that underflows/overflows wrap around within the 32-bit space ($[0, 2^{32}-1]$).

---

### Pattern 5: Global Memory & Archive Lazy-Loading Access
*Original x86 Instruction:*
```assembly
REP MOVSB                          ; Copy unpacked stadium texture buffer
```
*Hooked C Translation in `host/core.c`:*
```c
void hook_memcpy(uint32_t dst_addr, uint32_t src_addr, uint32_t count) {
    check_lazy_archive_page(src_addr, count); // Pages in 64KB block if reading from archive
    memcpy(cricket_translate(dst_addr), cricket_translate(src_addr), count);
}
```
*How it behaves on 64-bit Host:*
- When the game loads stadium textures from `.big` files, `host/core.c` intercepts the memory copy.
- It verifies if `src_addr` falls within an unpaged archive segment. If so, it dynamically decompresses a 64KB chunk from disk before completing the copy.
- This prevents loading the entire 575MB stadium archive into physical RAM at once.

## 3. Conclusion & Pointer Architecture Rule

**Final Audit Finding:**  
The recompiled game code strictly assumes a **32-bit address space**.
- Pointers stored in structures, globals, and vtables are always 32 bits wide (`uint32_t`).
- Direct pointer dereferences `*(uint32_t*)addr` require **either** that the process has memory mapped at virtual address `addr` (Strategy 1), **or** that an address wrapper macro `MEM(addr)` adds the base pointer `g_ram` (Strategy 2).
- Phase B.6 proves both strategies on live Android execution.
